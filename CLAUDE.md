# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Digital infrastructure for **ischlstrom.org**, an Austrian energy community (Energiegemeinschaft / EEG). A monorepo of three loosely-coupled parts that share a common PostgreSQL database:

- **`website/`** — SvelteKit 5 app: public site + authenticated member/board/finance portals. This is the main deployed application. User-facing text is German.
- **`middleware/`** — Django project (`eeg`) that owns and migrates the shared "middleware" Postgres schema. Rarely run as a server; it's the schema authority + Django admin.
- **`notebooks/`** — Jupyter notebooks for accounting, energy analysis, weather, and SEPA XML generation (see per-directory READMEs).
- **`Batteriemanagement/`**, **`scripts/`** — OpenHAB battery-control scripts and DB export/restore shell scripts. The control core is `Batteriemanagement/openhab/control/core.js` (adapter per inverter profile in `inverters/*/adapter.js`); before changing the charge regulation run the replay in `control/replay/` (README there, data exported from prod, CSVs gitignored). `scripts/ibm-provision/` is the s1 host side (root timer) of the zero-touch Pi provisioning; the website side lives in `website/src/lib/server/db/members/openhabProvision.js` + `routes/api/ibm/provision/` (plus `lib/server/ibmImage.js` for on-server SD image builds — needs xz/mtools in the Docker image and the `ischlstrom-images` volume —, `lib/server/secrets.js`, `lib/server/mailcow.js`, `lib/setupPhases.js`, and the member page `routes/(website)/user/[memberId]/speichermanagement/`), the Pi side in `Batteriemanagement/openhab/setup/00-provision.sh`, `prepare-sd.sh`, `firstboot/`. Pis update themselves: root timer `ibm-update` (`setup/09-install-updater.sh`) downloads package + `ibm-openhab.tgz.minisig` nightly when the package checksum changed, or within 10 min when the board requests it on `/board/openhab` (`update_requested_at` → status-push response `update: true`), verifies the minisign signature against the installed `setup/ibm-release.pub` (fail closed) and only then runs `setup/install-package.sh` from the new package; `build-dist.sh` signs with `~/.minisign/ibm-release.key` (private key never in the repo, `IBM_SIGN_KEY` overrides) and writes `static/ibm/VERSION` for the dashboard comparison. The bootstrap `static/ibm/install.sh` (first install, firstboot) trusts TLS, verifies the signature too once the Pi has the key, and ends in the same `install-package.sh`. OS packages update themselves too: `setup/11-install-apt-auto.sh` configures `unattended-upgrades` for the Debian archives plus the `Raspberry Pi Foundation` origin (kernel, firmware; the Debian default left those pending), daily from 03:40 with a reboot at 10:00 when required (daytime on purpose, so a Pi that fails to come back is noticed) (`INSTALL_APT_AUTO`, `APT_AUTO_REBOOT`, `APT_AUTO_REBOOT_TIME` in `ibm.conf`); openHAB, NodeSource and Tailscale stay manual. Debian's `openjdk-21` does update automatically, and a running JVM can no longer spawn processes after that (every `executeCommandLine` fails: heartbeat, rediscovery, system status; whole fleet 2026-10-28), so the apt hook `53ibm-jvm-restart` restarts openHAB when the JVM maps deleted JDK files, and `install-ibm.sh` runs the same check at its end. openhabian puts `/var/lib/openhab/persistence` (mapdb: feed-in counter, sun profile, capacity and house-load estimates, member settings) on a zram overlay that is only written back on a clean shutdown, so a power cut rolled pi-020 back three weeks (2026-10-09); `setup/12-install-persistence-disk.sh` comments that entry out of `/etc/ztab` (`INSTALL_PERSISTENCE_DISK`, effective at the next clean reboot, `/var/log` stays in zram; openhabian's `zsync.timer` is unsafe while openHAB runs and stays disabled). The battery feed-in sums (`/board/openhab`, member report, status-push response `einspeisung` with `woche_kwh`/`monat_kwh`/`gesamt_kwh` for the Main UI items `IBM_BATTERIE_NETZEINSPEISUNG_{WOCHE,MONAT,GESAMT}_KWH`) are computed in `lib/server/db/energy/batteryGridFeedIn.js` from plausible increments between consecutive status pushes (`batteryGridFeedInSql.js`, a drop or a jump above 10 kW × elapsed time counts 0), rolled up daily into `members_openhabcountersnapshot.battery_grid_delta_kwh` (migration 0040); the raw local counter is never shown. The WireGuard maintenance tunnel (`setup/08-install-wireguard.sh`, Pi → s1 `10.88.0.0/24`) is guarded by the root timer `ibm-wg-watchdog` (every 5 min): `wg-quick@wg0` is a oneshot unit that stays "active" after the tunnel silently dies, so the watchdog restarts it when the interface is gone or the last handshake is older than 10 min (`journalctl -t ibm-wg-watchdog`; check on s1 with `sudo wg show wg0 latest-handshakes`). SSH maintenance access through the tunnel uses a key next to the password login: `setup/13-install-maint-key.sh` adds the public key shipped in the signed package (`setup/ibm-maint.pub`, private part only in the workstation's `ssh-agent` as `~/.ssh/ibm-maint`) to `openhabian`'s `authorized_keys`, restricted to `from="10.88.0.1"`, plus passwordless sudo in `/etc/sudoers.d/90-ibm-maint` (`INSTALL_MAINT_KEY`, `MAINT_SSH_FROM`, `MAINT_SUDO_NOPASSWD` in `ibm.conf`); the Linux passwords stay valid, but the same step restricts SSH password logins to the tunnel (`/etc/ssh/sshd_config.d/10-ibm-tunnel-only.conf`: `PasswordAuthentication no` with a `Match Address 10.88.0.1` exception, named `10-` because sshd takes the first value per option; `SSH_PASSWORD_TUNNEL_ONLY`), so nothing logs in from a member's LAN; it is only applied while the tunnel has a fresh handshake and after `sshd -T` confirms the tunnel address still gets password auth. Without `ibm-maint.pub` in the package only the key part is skipped. Modbus-controlled inverters (every profile except the GEN24 `fronius`) have no device-side command expiry, so `setup/10-install-failsafe.sh` installs a root timer `ibm-failsafe` plus a boot reset that write the factory state via the profile's `inverter_failsafe_reset` when the core's heartbeat (`/var/lib/ischlstrom/requests/heartbeat`, touched by `core.js` after a confirmed reset) goes stale or openHAB is down (Hauptschalter OFF = one final reset, then the standby marker `failsafe-standby` keeps core, timer and boot reset off the inverter); the website mails the board about silent plants (`lib/server/mail/notifications/ibmAlerts.js`, column `offline_alerted_at`) and, when `SIGNAL_*` is set in `.env`, sends the same alert per Signal via the `signal-cli-rest-api` container on s1 (`lib/server/signal.js`, test with `node scripts/signal-send.js`, setup in `docs/server-setup.md`). System alerts for the Pis (SD card ≥70%, CPU ≥60 °C, RAM ≥50%, any swap in use; hysteresis 5 points, one Signal message per plant on entry and an all-clear on exit, state in column `system_alerts`, Signal only, no mail) come from `lib/server/mail/notifications/ibmSystemAlerts.js` (cron `checkSystemAlerts`, every 5 min). Analysis and on-site test plan: `Batteriemanagement/openhab/inverters/failsafe-modbus.md`. Fleet health overview: `/board/openhab/health` (`routes/(website)/board/openhab/health/`, checks in `src/lib/ibmHealth.js` without DB access, data from `lib/server/db/members/openhabHealth.js`; the tunnel column reads `wg_handshake_at`, stamped every minute by `ibm-provision-sync.sh` on s1 from `wg show`, migration 0038). Inverter-driven battery maintenance (Fronius calibration charge: full, then ~1 kW down to empty regardless of commands and the minimum SOC; service/protective charges) is reported by the adapter's optional `ibmBatteryMaintenance()` (`ChaSt` 7 / Solar API `Battery_Mode`), published as item `IBM_BATTERIE_WARTUNG` and push field `batterie_wartung`; while it lasts `core.js` pauses control, discards that night's house-load measurement and skips charge-rate samples, and the health page rates such a night as info. Plan and status: `docs/ibm-setup-vereinfachung.md`; board-member guide (LaTeX/PDF): `docs/setup/`. Secrets in `members_openhabstatus` are AES-GCM encrypted with `IBM_SECRET_KEY` from `website/.env` (never rotate casually). Everything a Pi reports (hostname/`anlage`, `wg_public_key`, `inverter_type`) is validated against `src/lib/ibmNames.js` at the endpoints and again in the sinks (`ibmImage.js`, `renderOpenhabianConf`, `ibm-provision-sync.sh`); code redemptions are counted in `provision_redemptions` (migration 0039) with a Signal alert from the second one. DSGVO consent for the Speichermanagement is recorded in `members_consent` (member page gates on it, board dashboard shows a badge); the consent text lives in `ConsentText.svelte` on the member page + the paper fallback `docs/setup/speichermanagement-einverstaendnis.tex` — change both together and bump the version in `website/src/lib/consent/speichermanagement.js`.

## Databases (important architecture)

Two shared PostgreSQL databases:

1. **middleware DB** (`ischlstrom_middleware`) — schema is defined and migrated by the Django project in `middleware/`, but the SvelteKit app reads/writes it **directly via a `pg` pool** (`website/src/lib/server/db/db.js` → `middlewareDbPool`), *not* through Django. When changing tables, update Django models/migrations in `middleware/` AND the raw SQL in `website/src/lib/server/db/`.
2. **authjs DB** — session/user store for Auth.js (`authDbPool`, `@auth/pg-adapter`). Separate from the middleware DB.

DB credentials come from `website/.env` (gitignored). Notebooks and Django connect via a `.pg_service.conf` service named `eeg-middleware` (also gitignored, alongside `.pgpass`).

## website/ (SvelteKit 5 + Tailwind 4 + Flowbite)

Commands (run from `website/`):
- `npm run dev` — dev server (cron jobs are disabled in dev)
- `npm run build` — production build (adapter-node)
- `npm run preview` — preview the production build
- `npm run check` — type-check via `svelte-check` (uses `jsconfig.json`)
- `npm run start` — run the built server (PORT=8080, expects reverse-proxy headers)

There is no test runner and no lint script configured.

Deploy: `./deploy-server.sh` rsyncs the tree to the server; on the server `./update-docker-container.sh` rebuilds the Docker image and `./run-docker.sh` runs it (maps host 3000 → container 8080, TZ Europe/Vienna).

Key conventions:
- **Auth & authorization** live in `src/auth.ts` + `src/hooks.server.js`. Login is passwordless magic-link email via Nodemailer (`@auth/sveltekit`). Authorization is route-prefix based in `authorizationHandle`: route groups `/(website)/board`, `/finance`, and `/user` require a session and redirect to `/login` otherwise. Adding a new protected area means adding its prefix there.
- **Scheduled jobs** are registered with `node-cron` inside `cronHandle` in `hooks.server.js` (weather fetch, activation reminders, materialized-view refresh). Every job early-returns when `dev` is true. An `initialized` guard prevents double-scheduling under HMR.
- **Server-only DB/mail/nextcloud code** lives under `src/lib/server/` (organized by domain: `db/energy`, `db/finance`, `db/members`, `db/weather`, `mail`, `nextcloud`). Never import these from client code. Environment variables are read via `$env/dynamic/private` only (the `.env` is mounted into the container at runtime, not built into the image; `$env/static/private` would inline secrets into the build).
- **Prices and tariffs** (EEG Bezugs-/Einspeisetarif, Netz OÖ Netzentgelte per year, EEG rebates, levies, competitor tariffs such as Energie AG) live in one place: `src/lib/tariffs.js` (`TARIFFS` by year, `CURRENT`, `tariffFor(year)`). Homepage, FAQ, `/board/energy` YearlySummary and the local-EEG assessment on `/board/map` read from it; never hard-code a ct/kWh value in a page, extend the store (new year on top, old years stay).
- **Monthly energy report** (member e-mail): `src/lib/server/mail/reports/` (`energyReportData.js` builds the numbers, `energyReportContent.js` turns them into a neutral block model with all wording and chart scales, which `energyReportTemplate.js` renders as table-based mail HTML + text and `energyReportPdf.js` as the attached PDF via pdfkit; change content only in the model. `monthlyEnergyReport.js` is the cron job, hourly 08:30-18:30) with the SQL in `src/lib/server/db/energy/monthlyReport.js`. The job sends the previous month once `daily_metering_quality` covers it completely (from the 15th regardless), exactly once per member via `members_energyreportlog`, rate-limited for the mail server to `MAX_PER_RUN` (40) mails per run with a 3 s pause, so the whole community (~370) goes out over one day; members opt out via `members_member.energy_report`. Members with a battery counter (`members_openhabcountersnapshot`) additionally get the section "Ihr Speichermanagement" (battery feed-in per day, active days, community uptake in dark hours vs. daylight via `weather_weatherdata.shortwave_radiation = 0`, fleet total); only the counter snapshots are durable, the 30-day status history does not cover a report month. Recipients are gated by `ENERGY_REPORT_RECIPIENTS` in `.env` (unset = off, comma-separated addresses = test phase, `all` = everyone; prod `.env.s1` is `all` since 2026-09-19). Data and template modules use relative imports only, so `node scripts/energy-report.js --member <nr> (--out file.html | --to address [--bcc address])` renders/sends the same report without SvelteKit and without touching the log.
- **Speicherrechner** (member area, `/user/[memberId]/speicherrechner`, only in the navigation for members with an active GENERATION point; during the pilot additionally limited to the member numbers in `PILOT_MEMBERS` in `src/lib/server/db/energy/batteryCalculator.js`, currently only member 1, other members get a 404 and no navigation entry, empty list = open for all): suggests a battery size from the member's own 15-min grid import/export of the last twelve full months. `src/lib/server/db/energy/batteryCalculator.js` delivers the series plus the community's uncovered demand per quarter hour (from `station_metering_15min`, night-hours fallback without the view); the simulation `src/lib/batteryCalculator.js` is pure JS and runs in the browser (self-use, optional discharge into the EEG bounded by the community deficit, optional peak shaving for the power-based grid fee from 2027). Price defaults and the provisional 2027 power tariff live in `BATTERY_CALCULATOR` / `importPricesCt()` in `src/lib/tariffs.js` — update the €/kW values once the E-Control tariff ordinance is out.
- **Newsletter contacts** (Keila on s1, `newsletter.ischlstrom.org`): the cron `syncNewsletterContacts` (daily 04:50, `src/lib/server/newsletter/keilaSync.js`) mirrors every member with at least one ACTIVE measurement point into Keila via its REST API, one contact per e-mail address (`src/lib/server/db/members/newsletter.js` builds the list, `src/lib/server/newsletter/keila.js` is the pure API client + CSV writer). Contacts carry `data.mitglied = true` (plus `mitgliedsnummer(n)`, `ort`, `erzeuger`); only those are updated or deleted, the status (unsubscribed) is never sent. Needs `KEILA_API_URL` + `KEILA_API_KEY` in `.env` (unset = off). `node scripts/keila-contacts.js --sync --dry-run` previews, `--out file.csv` writes the same list for a manual import, `--sync --delete-others` is the deliberate cleanup that also removes non-member contacts. Keila segment "Mitglieder" filters on `{"data.mitglied": "true"}` (string, a JSON boolean crashes the filter); setup in `docs/server-setup.md`.
- **Member master data** come from the EEG-Faktura export `RC101533-EEG-Masterdata-YYYYMMDD.xlsx` in Nextcloud (one row per Zählpunkt), imported on every visit of `/board/members` and `/board/members/import` by `src/lib/server/nextcloud/members/memberdata.js` (upsert on `Mit. Nr.` and on Zählpunkt; rows that disappear from the sheet are never removed). A member number that the sheet lists for two different persons (name or e-mail differ) is skipped entirely and reported on the import page (`masterdataConflicts.js`, no SvelteKit imports so it can be tested against the real sheet); the fix belongs in EEG-Faktura, not in the DB. Besides the conflicts, the import runs the masterdata checks from the Rust checker (`masterdataChecks.js`, pure module with `node:test` tests, `npm test`): ACTIVE meter points without `Zp. Tarifname`, ACTIVE meter points without `aktiviert`, and ownership transfers (a Zählpunkt under several member numbers: valid when the owners' periods do not overlap and at most one is ACTIVE; end dates in year 2999/9999 count as open); findings are returned as `checks` and shown in the amber box on `/board/members/import`, they belong in EEG-Faktura, not in the DB. The import also stores `activated_at`, `deactivated_at` and `subscription_name` on `members_measurementpoint` (migration 0042); the same columns are refreshed daily at 04:40 on s1 by `notebooks/energyData/eegfaktura_masterdata.py` (`eegfaktura-masterdata.timer`, JSON from `GET /api/master/masterdata` with Basic auth; the JSON has no e-mail, address or tariff, so new members still need the sheet; a Keycloak password grant for the xlsx export is not allowed by the EEG-Faktura client).
- **Abrechnungsprüfung** (`/board/energy/pruefung`, board area): replaces the Excel energy report plus eeg-tools checker for the billing run. `src/lib/server/db/energy/billingCheck.js` computes per meter point the missing and L3 quarter hours inside its active window (window = period ∩ `activated_at`/`deactivated_at`, ACTIVE without date counts from the period start; days in Europe/Vienna, 92/100 slots on DST days; L3 from `metering_measurement.quality`, the energystore `qov` stored by `eegfaktura_import.py` since migration metering 0006, NULL for older data counts as present and reliable), the period totals from `daily_metering_quality` and the activation windows from the three sources (masterdata columns, latest podlist in `members_podlistentry`, energystore `store_period_begin/_end` written by the import's `--metadata` call). `src/lib/billingCheck.js` is the pure evaluation (status per point, day ranges, Nachforderung text, fingerprint, Signal text; tests in `billingCheck.test.js`). Cron `checkBillingReadiness` (06:10, `mail/notifications/billingCheckAlerts.js`) evaluates the last full quarter until it is marked billed on the page (`metering_billingcheck`, migration metering 0007) and sends a Signal only when the fingerprint changes, plus a weekly reminder from 14 days after quarter end while not green. EEG-Faktura's `POST /meteringpoint/syncenergy` needs a Bearer token and the Keycloak client allows no direct access grant, so the page's "Nachforderung direkt senden" form takes the token pasted from the board member's own EEG-Faktura browser session (`lib/server/eegfaktura/syncEnergy.js`, one range per Zählpunkt from first to last missing day, token never stored); the copyable text block remains the fallback.
- Routing uses the `(website)` route group; `board/*` is the admin area. Dynamic user pages are `user/[memberId]`.
- `csrf.checkOrigin` is on (SvelteKit default); `svelte.config.js` no longer disables it. The Origin check needs the fixed `ORIGIN` env (set in the `start` script), not the forwarded headers.

## notebooks/

Analysis and back-office notebooks (run with the repo-root `.venv`). Notable areas: `finance/` (SEPA XML for direct debits/credits — `XML Lastschriften`, `XML Gutschriften`, George bank CSV import, tax/annual-close), `energyData/` (EEG-Faktura energy data: `eegfaktura_import.py` pulls 15-min values from the energystore API and runs daily on s1 via `scripts/eegfaktura-import/`; the xlsx report notebook is the manual fallback), `weather/` (Open-Meteo import), `eegfaktura/` (EEG-Faktura API), `forecast/` (energy forecast — see below). Data files under these directories are gitignored.

`weather/backfill_openmeteo.py` is the canonical loader for `weather_weatherdata` (archive API for the past, forecast API for the rest, `--check` reports coverage gaps); the notebooks next to it only write the original eleven columns and are superseded.

`forecast/` predicts the community 15-min series for the days the EEG-Faktura export does not cover yet. `eeg_forecast.py` holds the logic (also runnable as a CLI), `Energieprognose.ipynb` drives it, `forecast/README.md` explains the model. `--store` writes a run to `metering_energyforecastrun` / `metering_energyforecast` (runs are never overwritten, which is what makes the later forecast-vs-actual comparison in the `energy_forecast_vs_actual` view possible); the website reads the newest run at `/vorhersage`. On s1 the forecast runs daily at 05:30 via `eeg-forecast.timer` (`scripts/eegfaktura-import/`, `--refresh --days 30 --days-ahead 14 --store`), independent of the 05:00 import; after a manual Excel import run the notebook first (it refreshes `daily_metering_quality`), then `eeg_forecast.py --refresh --days 30 --store`. Two things to know when touching measurement data anywhere: some deliveries are only partial (rows present, most points all-zero — `MIN_REPORTING_SHARE` detects that); and `Anteil gemeinschaftliche Erzeugung` equals the total community generation, while `Eigendeckung` is what members actually consumed. Since the new data supply (July 2026) delivered days are trusted as-is — the former 120-day maturity gate (`DATA_MATURITY_DAYS`, `actual_is_mature`) is gone; `actual_is_mature` remains in the view as a constant `true` for compatibility.

## eeg-tools/ (Rust workspace + Tauri client)

Checks the EEG-Faktura exports (masterdata, podlist, energy report) before billing. A Cargo workspace of three crates, each imported as a git subtree with its own history on 2026-11-01: `eegfaktura-datalib/` (xlsx loaders in `src/eegfaktura/loader/`, all checks in `src/eegfaktura/checks/`), `eegfaktura-checker/` (CLI: `cargo run -p eegfaktura-checker -- <folder>` picks the newest `*EEG-Masterdata-<date>.xlsx`, `*ZP_PODLIST.xlsx` and `*Energy-Report-<start>_<end>.xlsx` in that folder, exit code 1 when a check finds something), `eegfaktura-client/` (Tauri 2 + SvelteKit GUI over the same lib, `pnpm install && pnpm tauri dev` from its directory). Tests: `cargo test -p eegfaktura-datalib` and `cargo test -p eegfaktura-checker` run against the anonymized workbooks in `eegfaktura-datalib/fixtures/` (gitignored like `test-files/`, so generate them locally first with `.venv/bin/python -I eeg-tools/scripts/anonymize-fixtures.py` from the real exports in the gitignored `test-files/` directories, `--verify` proves no name, IBAN, address or real meter point id survives, `--map` shows what an id or member number maps to when adjusting tests; meter point ids become `AT999` + 28 digits, re-running is deterministic). The real exports stay only locally (`eegfaktura-checker/test-files/` holds full-month reports for manual runs). The checker takes `--format json` (all check results as one JSON document on stdout, errors on stderr) and `--nachforderung` (one line per meter point: id, name, missing and L3 days as ranges `2026-10-01..2026-10-03, 2026-10-17`, the list for the data request to Netz OÖ); exit 1 on findings, 2 on usage/file errors. The masterdata and podlist loaders and the energy report's Summary sheet resolve columns by header name (the export inserted two `Beitrittsgebühr` columns before `Zählpunkt` in November 2026); only the Energiedaten sheet stays positional because its transposed layout has no header row. Plan to replace the manual export/check cycle with DB-side checks, a board page and Signal alerts: `docs/eegfaktura-pruefung-automatisierung.md` (2026-11-01). Built so far: the **podlist mail intake** (`website/src/lib/server/podlist/`: `sheet.js` parses the `ZP-List` sheet by header names, one row per activation window, `active_until` NULL = open; `db.js` stores every delivery in `members_podlistimport` + `members_podlistentry` (migration 0041) and computes the deviations for `/board/members/import`; `mailbox.js` reads info@ischlstrom.org over IMAP (`IMAP_HOST/PORT/USER/PASSWORD` in `.env`, app password), matches the subject `RC101533 Zählpunktliste <YYYYMMDD-HHMM>`, never marks or moves mails and dedupes on Message-ID; cron `importPodlistMails` every 10 min archives the xlsx next to the masterdata sheet in Nextcloud and sends a Signal summary). `node scripts/podlist-fetch.js --dry-run [--imap-env .env.s1]` tests the mailbox without writing, `--file <xlsx>` imports a local podlist.
